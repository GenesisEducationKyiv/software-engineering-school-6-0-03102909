# ADR-001: Вибір інструменту для фонових задач (cron jobs, scheduling)

**Дата:** 2026-05-08  
**Автор:** Sofiia Perkova

## Контекст

Додаток потребує надійної системи для виконання фонових задач. Необхідно:

- Періодично сканувати GitHub на наявність нових релізів
- Ставити в чергу задачі на відправку сповіщень користувачам
- Забезпечити стійкість до збоїв, повторне виконання при помилках та гарантію виконання задачі у випадку перезавантаження або падіння сервера

## Розглянуті варіанти

### 1. In-memory планувальники (croner, node-cron)

- **Плюси:** Прості в налаштуванні, не вимагають жодних баз даних або зовнішніх залежностей
- **Мінуси:** Дані зберігаються лише в оперативній пам'яті. Якщо сервер падає — всі задачі втрачаються. Також складно масштабувати додаток (при запуску кількох копій сервера cron спрацює на кожному з них одночасно)

### 2. BullMQ (на базі Redis)

- **Плюси:** Висока швидкість обробки, потужний функціонал для черг, мікросервісів та воркерів
- **Мінуси:** Хоча Redis і використовується в стеку проєкту, зберігання критичних черг виключно в Redis вимагає додаткового налаштування стійкості даних (наприклад AOF або RDB snapshots), щоб уникнути їх втрати при збоях інфраструктури

### 3. pg-boss (на базі PostgreSQL)

- **Плюси:** Працює поверх існуючої PostgreSQL бази даних. Гарантує збереження черг на рівні реляційної БД. Має вбудовану підтримку cron-виразів та розумні механізми повторного виконання
- **Мінуси:** Трохи більше навантаження на основну базу даних (PostgreSQL), проте для масштабів проєкту на даний момент це прийнятно

## Прийняте рішення

Обрано **pg-boss** як основний інструмент для управління чергами та розкладом виконання задач (cron jobs)

### Обґрунтування:

1. **Максимальна надійність:** Оскільки всі задачі записуються безпосередньо в таблиці PostgreSQL, ми гарантуємо, що жодна задача сканування релізів або відправка листа не зникне при збої додатка
2. **Єдине джерело правди:** Використання PostgreSQL і для бізнес-даних, і для задач спрощує архітектуру та бекапи (все зберігається в одному місці)
3. **Зручний функціонал:** Вбудована підтримка відкладеного виконання, cron-розкладів та автоматичної обробки провалених задач

## Наслідки

- **Позитивні:** Надійна архітектура фонових процесів, збереження історії та статусу виконання задач. Легкий дебаггінг, оскільки стан черги можна переглянути через звичайні SQL-запити або клієнт на зразок pgAdmin
- **Негативні:** Схема бази даних розширюється службовими таблицями `pg-boss`, які час від часу потрібно очищати від старих виконаних задач (хоча pg-boss має вбудований механізм автоочищення)
