# ADR-002: Перехід до асинхронної мікросервісної архітектури для відправки сповіщень

**Дата:** 2026-06-09  
**Автор:** Sofiia Perkova  
**Статус:** Прийнято

## Контекст

Процес відправки email-сповіщень винесено в окремий мікросервіс. Спочатку розглядався варіант синхронної взаємодії через HTTP. Проте для фонових задач це поганий підхід: запити блокують виконання, сервіси стають сильно залежними один від одного, а якщо мікросервіс впаде - задачі просто загубляться

Тому виникла необхідність в асинхронній архітектурі, де моноліт просто віддає задачу, а мікросервіс її забирає і виконує

## Розглянуті варіанти

### 1. Синхронні запити (HTTP / REST / gRPC / JSON-RPC)

- **Плюси:** Найпростіша реалізація, не потребує додаткової інфраструктури (для HTTP)
- **Мінуси:** Навіть при використанні швидких RPC-протоколів зберігається жорстка зв'язність: відсутня гарантія доставки при падінні мікросервісу, а моноліт змушений чекати на відповідь або самостійно реалізовувати механізм повторних спроб

### 2. BullMQ (на базі Redis)

- **Плюси:** Дуже швидкий, створений спеціально для черг повідомлень у Node.js
- **Мінуси:** За своєю суттю є повним аналогом `pg-boss`, але вимагає використання Redis. Оскільки Redis у нас використовується лише як кеш без налаштованої персистентності, є ризик втрати задач при перезавантаженні

### 3. RabbitMQ

- **Плюси:** Спеціалізований, потужний брокер повідомлень, який чудово підходить для комунікації мікросервісів
- **Мінуси:** Вимагає розгортання та підтримки нового компонента інфраструктури, що на даному етапі є надмірним ускладненням

### 4. pg-boss (існуюча база PostgreSQL)

- **Плюси:** `pg-boss` вже впроваджений у проєкті. Використовуючи його як брокер повідомлень, моноліт записує задачі у таблиці `pg-boss`, а мікросервіс працює як воркер, що асинхронно їх вичитує. Забезпечується надійна гарантія доставки
- **Мінуси:** БД виступає в ролі брокера, що може стати вузьким місцем при дуже високих навантаженнях. Крім того, це створює спільну базу даних між монолітом та мікросервісом, що порушує принцип повної ізоляції інфраструктури

## Прийняте рішення

Обрано архітектуру асинхронного мікросервісу на базі **pg-boss**

### Обґрунтування:

1. **Відмова від HTTP:** Асинхронний підхід через черги робить систему стійкою. Якщо мікросервіс впаде, моноліт продовжить працювати і складати задачі в чергу
2. **Ізоляція:** Задачі формуються так, що мікросервіс отримує одразу всі необхідні дані. Завдяки цьому мікросервіс взагалі не лізе в основні таблиці
3. **Використання існуючих інструментів:** `pg-boss` та PostgreSQL підходять на даному етапі і не вимагають нових інструментів
4. **Заділ на майбутнє:** RabbitMQ є кращим транспортом, проте його впровадження залишено на майбутнє, щоб не ускладнювати інфраструктуру прямо зараз

## Наслідки

- **Позитивні:** Максимальна стійкість, незалежність сервісів, відсутність спільних бізнес-таблиць
- **Негативні:** PostgreSQL тимчасово виконує роль брокера, що є компромісом до можливої міграції на RabbitMQ у майбутньому
